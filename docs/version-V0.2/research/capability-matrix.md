## 1. 结论先行

1. **0.2 最终基线（已拍板）：选项 C —— 0.1 P0–P8 全功能对齐 + P9 五项**。核心闭环 = 版本/需求/澄清 → 设计/用例/确认 → 执行波次/证据 → 问题/报告；P9 = D59/D63/D65/D67 + 问题重开/合并/跨波次去重。
2. **0.2 的重写集中在“控制面”**：版本生命周期、需求/用例版本与确认、Agent 团队运行时、任务板/频道、上下文工程、前端信息架构。
3. **0.1 的确定性底座应移植/改造，而不是重写**：身份、LLM 网关、事件/SSE、文件与证据、审计/幂等/限流、资源、执行器协议、报告确定性渲染、fake LLM/测试夹具。
4. **0.2 必须覆盖 0.1 P0–P8 的全部已交付能力**：完整代码智能（索引/影响/锚点/事实复核）、视觉断言、质量中心/评测、全局搜索/待办、Agent 中心、全局问题/报告中心、探索链路 v2 都纳入 0.2；不再以“后置 0.3”为由裁剪。0.3 只承接 P0–P8 之外的新能力（多用户协作、非 PG、外部工单等）。
5. **基础代码读取是底线，不是上限**：设计 Agent 既能读 tree/file，也能用完整代码智能（索引/diff/影响/锚点）。

---

## 2. 处置分类

| 标记 | 含义 |
|---|---|
| **移植** | 领域模型与实现基本可复用，主要改装配/接口/边界 |
| **改造** | 保留领域模型与大部分实现，改流程、契约、并发或存储 |
| **重写** | 领域模型或控制流发生本质变化，0.1 实现只作参考 |
| **新增** | 0.1 不存在或仅有意向，需要新领域/新运行时 |
| **后置** | 0.2 不做，列入 0.3 能力回归 |
| **退役** | 0.1 的概念/代码不再保留，由新机制替代 |

规模为相对量级（S/M/L/XL），不是工期承诺。

## 4. 0.2 交付基线选项

### 选项 A：AI 核心闭环 + P9（未选，仅保留决策过程）

**包含**：A1–A6、B1–B3、C1–C3、D1/D2/D4、E1–E5、F1/F2、G1/G3/G4、H1–H5、I1/I2。
**不含**：B4 完整代码智能（保留 tree/read）、D3 视觉断言、F3 全局中心、G2 Agent 中心控制台/评测、H6 搜索/待办/链路。
**理由**：0.2 的目标是证明“AI 驱动半自主闭环”可用；先把控制面、版本/需求/用例模型、任务板/上下文、对话式 UI 跑通，再回归差异化能力。
**主要风险**：设计质量因缺少代码智能下降；0.3 需要补回；P9 的 D67 仍是重工程。

### 选项 B：核心闭环 + 代码智能 + 视觉断言 + P9

**在 A 之上加回**：B4（索引/diff/影响/锚点/事实复核）、D3（视觉断言）。
**理由**：保留 0.1 的差异化能力（代码感知、视觉证据），对外叙事更完整。
**主要风险**：范围显著变大；代码智能与视觉断言都需要重新适配新用例版本/波次模型；0.2 周期与验证成本上升。

### 选项 C：0.1 全功能对齐 + P9（已选）

**在 B 之上加回**：F3 全局中心、G2 Agent 中心/评测、H6 搜索/待办/链路，以及 0.1 的所有硬化项。
**理由**：0.2 作为完整替代版本，功能不回退。
**主要风险**：控制面重写 + 全能力回归 + P9 同时进行，范围失控概率最高；必须用独立能力波次与验收门禁控制风险，不能一次性 big-bang。

---

## 5. 建议

1. **采用选项 C**：0.2 = 0.1 P0–P8 全功能对齐 + P9 五项；0.1 仅作参考，不保留接口/数据兼容。
2. 0.2 内部按能力波次推进：平台/运行时 → 澄清 → 设计 → 执行/交付 → 全功能对齐（代码智能/视觉/质量/搜索/待办/Agent 中心）→ P9 → 硬化/验收；每波必须能独立演示与回归。
3. 0.3 只承接 P0–P8 之外的新能力（多用户协作、非 PG 目标库、外部工单/CI/IM 等），不再把 0.1 已交付能力作为 0.3 的回归项。
4. 0.1 的确定性底座（身份/LLM/事件/存储/审计/资源/执行器协议/报告确定性渲染/fake LLM）优先移植，避免重复踩坑。
5. 所有“重写”项都必须以新数据模型和任务板/上下文契约为准，不能把 0.1 的 8 状态机、整版冻结、单活跃批次/会话、问题终态等旧假设带进 0.2。
